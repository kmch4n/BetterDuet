# DUET の挙動

BetterDuet の設計の前提になる、DUET 側の挙動をまとめた文書です。DUET には公開された仕様がなく、挙動にも直感に反するところが多いため、確かめたことをここに書き足して育てていきます。

- 本文には、実際の画面で確かめた事実だけを書き、確かめた日付を添える
- 推測は「未検証」と明記する。確かめたら本文に移し、日付を付ける
- 実験をしたら、末尾の「観察ログ」に手順と結果を残す。本文の記述は、どの実験で確かめたかを `E-NNN` で示す
- DUET 側の更新で挙動が変わることがある。前提が崩れた疑いがあるときは、この文書から確認し直す

## 技術構成

2026-10-17 に確認しました。

- サーバー側は Java の Seasar2 / Teeda 系のフレームワークで作られています。Ajax は `Kumu.Ajax.executeTeedaAjax` を使います
- 画面側は jQuery 1.10.1、jQuery UI 1.10.3、jquery.cookie で動いています。iframe は使っていません
- 共通のスクリプトは `/front/js/` 以下にあり、ログインしなくても取得できます（`common.js`、`global.js`、`menu.js`、`ajax.js`、`jquery-kss.js`）
- 学生向け画面の URL は `/gakusei/html/fb/fbNNN/FBNNNNNG.html` の形で、末尾の `FBNNNNNG` が画面 ID です

## 入口

2026-10-17 に確認しました。

1. 同志社大学の Web Single Sign-On（`doshisha.ex-tic.com`）のポータルで「DUET」を押すと、新しいタブで DUET が開きます
2. 最初に「大学からのお知らせ」（`FB01090G`）が表示されます
3. 「DUETホーム画面へ」を押すと、ホーム（`FB01002G`）に進みます。これは `form1` のアクション `goHome` の POST です

ポータルからの入場は、`FB01090G.html` への GET 1回だけです。リダイレクトは挟まりません（E-008）。

### 入場ページは SSO を通らなくても開ける

`FB01090G.html` は、ポータルを通らずに URL を直接開いても、`fetch` で GET しても、同じように入場ページが返ります。セッションが壊れたあとでも、これで新しいセッションが始まり、そのままホームやほかの画面へ進めます（E-009、E-010）。Shibboleth のログインが生きている間に限ると考えられます。Shibboleth のログインが切れた状態は未検証です。

ただし、DUET のセッションが生きている状態で `FB01090G.html` を GET すると、ほかのページの GET と同じくエラーになり、セッションが破棄されます（E-006）。

## 画面遷移の仕組み

2026-10-17 に確認しました。

画面のリンクはすべて `href="#"` で、遷移先を URL では持っていません。リンクを押すと、ページ内の隠しフォームを POST して次の画面を表示します。

- 各画面には `unloadform`、`member`、`form1`、`menuform` の4つのフォームがあります（ホームの場合）
- リンクの `onclick` は `doActionWithHakiCheck('menuform', 'goFb17001g', …)` の形で、第1引数がフォーム ID、第2引数がアクション名です
- 送信時、`<フォームID>:__link_clicked__` に `<フォームID>:<アクション名>` が入ります（例：`menuform:goFb17001g`）
- サイドメニューの各項目は、`id` が画面 ID（例：`FB17001G`）、アクション名が `goFb` + 画面 ID の数字部分 + `g` です
- 履修登録などの受付期間外の項目は、`li.disabled` になりリンクがありません

### フォームには「サーバーの現在の画面」が埋め込まれている

フォームの送信先（`action`）と、フォームを識別する hidden 項目の名前に、サーバーが「いま表示している」と考えている画面のパスが入っています。

| 表示中の画面 | フォームの `action` | hidden 項目の名前 |
|---|---|---|
| ホーム | `/gakusei/html/fb/fb020/FB02001G.html` | `menuform/html/fb/fb020/FB02001G.html` |
| お知らせ | `/gakusei/html/fb/fb017/FB01701G.html` | `menuform/html/fb/fb017/FB01701G.html` |

hidden 項目の値はフォーム ID（例：`menuform`）です。アドレスバーの URL は、直前に POST した先のパスになるため、表示中の画面とは一致しません。

### トークン

`form1:token`（32文字）はセッションごとに1つで、画面を移っても値は変わりません（E-001）。SSO からログインし直すと別の値になります。

### Cookie

2026-10-17 に検証用の拡張機能で属性を確認しました（E-007）。値は読んでいません。

| 名前 | パス | 属性 | 有効期限 | 役割 |
|---|---|---|---|---|
| `JSESSIONID` | `/gakusei` | HttpOnly | ブラウザを閉じるまで | DUET 本体（Java）のセッション |
| `_shibsession_…` | `/` | HttpOnly、Secure | ブラウザを閉じるまで | Shibboleth のログイン |
| `AWSALB`、`AWSALBCORS` | `/` | | 7日 | ロードバランサーの振り分け |
| `clicked` ほか | `/` | | ブラウザを閉じるまで | 画面の表示状態（`menu.js` などが使う） |

DUET のセッションは2層になっています。ログインそのものは Shibboleth が持ち、画面の状態は `JSESSIONID` のセッションが持ちます。「ページ間の移動でエラー」で破棄されるのは `JSESSIONID` 側で、Shibboleth のログインは残ります。そのため、入場ページを開き直すだけで入り直せます。

## セッションが破棄される条件

2026-10-17 に確認しました。BetterDuet が解決する問題の核心です。

サーバーはセッションごとに「現在の画面」を1つだけ持っています。これに合わないリクエストを受けると、「ページ間の移動でエラーが発生しました」と表示し、**そのセッション自体を破棄します**。同じセッションを使っているほかのタブも、次の操作で「認証エラー」になります。

確認した条件は次のとおりです。

| 操作 | 結果 | 実験 |
|---|---|---|
| DUET のページ URL を新しいタブで直接開く（GET） | そのタブがエラーになり、セッションが破棄された | E-002 |
| 別の経路でサーバーの画面を進めたあと、古い画面のフォームを送信する | エラーになり、セッションが破棄された | E-003 |
| DUET を開いている状態で、SSO ポータルから DUET をもう一度開く | 新しいタブは開いた直後から「ページ間の移動でエラー」になった。元のタブも次の操作で「認証エラー」になった | E-006 |

最後の行は、利用者から見ると「何もしていないのにタブが無効になる」ように見える操作です。新しく開いたタブも使えないため、もう一度 SSO から開き直す必要があります。

### ブラウザの操作で GET が送られる場面

次の操作は、どれも表示中のページの URL への GET になります。DUET のページの URL は直前に POST した先なので、上の表の1行目と同じ理由でセッションが破棄されます。

| 操作 | 送られるもの | 実験 |
|---|---|---|
| 再読み込み | GET。DUET が読み込み時に `pushState` しているため、POST の再送信にはならず、確認ダイアログも出ない | E-014 |
| タブの複製 | GET | E-015 |
| メモリセーバーで破棄されたタブに戻る | GET。破棄されるとタブ ID も変わる | E-016 |
| ブラウザの再起動時のタブ復元 | GET（未検証） | |

### まだ確かめていない候補

- **無操作による期限切れ**：一定時間操作しないとセッションが切れる。時間は不明。約25分操作しなかったタブが生きていたことは確認した（E-005）
- **ロードバランサーの振り分けの変化**：`AWSALB` による振り分け先のサーバーが変わると、そのサーバーにセッションがないため切れる可能性がある

## 拡張機能でできることを確かめた方法

2026-10-17 に確認しました。

| 方法 | 結果 | 実験 |
|---|---|---|
| 同じセッションの `fetch` で、画面のフォームと同じ内容を POST する | 通常のクリックと同じ画面の HTML が返った。サーバーの現在の画面もその画面に進んだ | E-003 |
| 古い画面のフォームの `action` と hidden 項目名を、最新の画面のものに書き換えてからメニューを押す | 正常に遷移した | E-004 |
| `fetch` でメニューのアクションを送り、サーバーを古いタブの画面まで戻してから、古いタブのフォームをそのまま送信する | 正常に遷移した | E-004 |
| セッションが壊れたあと、`fetch` で入場ページを GET し、`goHome`、メニューの順に POST する | 新しいセッションで目的の画面まで進めた。SSO ポータルは通っていない | E-010 |
| DUET の存在しないパス（`/betterduet-landing`）を開く | サーバーは 404 を返すだけで、セッションに影響しなかった。拡張機能のスクリプトはこのページでも動く | E-011 |
| `declarativeNetRequest` で、`/gakusei/html/` への画面としての GET を、上の 404 のパスへリダイレクトする | GET は DUET に届かず、Chrome の中で 307 として付け替えられた。セッションは生きたままだった | E-012 |
| 404 のページから、最新の画面の形のフォームを作って本当に送信する | タブに目的の画面が正常に表示された | E-013 |
| ページのスクリプトより先に（`document_start`、`world: "MAIN"`）`window.addEventListener` を差し替え、DUET の `popstate` の監視を登録させない | ブラウザの「戻る」を拡張機能だけが受け取れた。DUET の警告は出ず、ページも移らなかった | E-017 |

メニューのアクションはどの画面のフォームにもあるため、最新の画面の形に合わせればどこからでも送れます。画面固有の操作（一覧の行を押すなど）は最新の画面にはないため、先にサーバーをその画面まで戻す必要があります。

`fetch` の GET と POST は、`declarativeNetRequest` の `main_frame` の条件に当たらないため、上の遮断ルールをオンにしたままでも送れます。

## 画面側の制限

2026-10-17 に `global.js` と `common.js` を読んで確認しました。

- **戻る**：`history.pushState` と `popstate` で「戻る」を検知し、警告を出して止めます
- **キー操作**：`document` の keydown で、F5、Esc、F11、F12、Ctrl+D/N/R/S/T/U/W、Shift+F10、Alt+←/→、入力欄以外での Backspace を無効にしています。入力欄で Enter を押すと、`id` が `enterDodoZikko` で終わる要素を押したことになります
- **二重送信の防止**：`checkOnceTime` により、1つの画面から送信できるのは1回だけです。送信後はすべてのリンクの `onclick` が `return false` に書き換わります
- **破棄の確認**：入力中に画面を離れようとすると、`hakiCheck` / `menuHakiCheck` が確認ダイアログを出します

## 観察ログ

実験の記録です。新しい実験は末尾に足し、番号は再利用しません。手順には、確認に使ったタブの数と各タブの画面を書きます。

### E-001 画面を移っても token は変わらない（2026-10-17）

ホームで `form1:token` を記録し、サイドメニューから「お知らせ」に移って再び記録した。値は同じだった。

### E-002 ページ URL を GET で開くとセッションが壊れる（2026-10-17）

タブ A でホームを開いたまま、タブ B でホームの URL（`FB01002G.html`）を直接開いた。タブ B は「ページ間の移動でエラー」になった。その後タブ A でメニューを押すと「認証エラー」になった。

### E-003 古い画面からの送信でセッションが壊れる（2026-10-17）

タブ A でホームを開き、同じタブから `fetch` で `menuform` を POST してサーバーを「お知らせ」に進めた。その後タブ A のメニュー「よくある質問」を押すと「ページ間の移動でエラー」になった。

### E-004 フォームの書き換えと再同期で遷移できる（2026-10-17）

- E-003 と同じ状態で、タブ A の `menuform` の `action` と hidden 項目名を、`fetch` で受け取った最新の画面のものに書き換えてからメニューを押した。「よくある質問」に正常に遷移した
- タブ A が「よくある質問」のときに、`fetch` でサーバーを「お知らせ」に進め、さらに `fetch` で「よくある質問」に戻した。その後タブ A の元のフォームのままメニュー「マニュアル」を押すと、正常に遷移した

### E-005 約25分の無操作ではセッションは切れない（2026-10-17）

E-004 の最後の操作から約25分後に、同じタブでメニューを押した。正常に遷移した。時間は作業の合間を目安にした概算で、正確に測っていない。

### E-006 SSO から開き直すと新旧どちらのタブも使えなくなる（2026-10-17）

1. SSO ポータルから DUET を開き（タブ F）、ホームまで進めた
2. タブ F には触らず、SSO ポータルからもう一度 DUET を開いた（タブ G）
3. タブ G は、開いた直後から「ページ間の移動でエラー」だった
4. タブ F でメニューを押すと「認証エラー」になった

### E-007 Cookie の属性（2026-10-17）

検証用の拡張機能（`experiments/probe`）の `chrome.cookies.getAll` で、`duet.doshisha.ac.jp` と `doshisha.ex-tic.com` の Cookie の名前と属性を取得した。値は取得していない。結果は本文の「Cookie」の表のとおり。

### E-008 SSO ポータルからの入場は GET 1回（2026-10-17）

検証用の拡張機能で通信を記録しながら、ポータルの「DUET」を押した。新しいタブで `FB01090G.html` への GET が1回（送信元は `https://doshisha.ex-tic.com`）送られ、200 が返った。リダイレクトはなかった。

### E-009 URL を直接開いて入り直せる（2026-10-17）

別のタブからホームの URL を GET してセッションを壊し、元のタブが「認証エラー」になることを確かめた。その後、そのタブのアドレスバーから `FB01090G.html` を直接開くと、通常の入場ページが表示された。「DUETホーム画面へ」、メニュー「お知らせ」と進めて、正常に表示された。

### E-010 fetch だけで入り直せる（2026-10-17）

E-009 と同じ手順でセッションを壊したあと、エラー画面のタブから `fetch` で `FB01090G.html` を GET した。エラーではない入場ページが返った。返ってきたページのフォームで `form1:goHome` を POST するとホームが、続けて `menuform:goFb01601g` を POST すると「よくある質問」が返った。

### E-011 404 のページはセッションに影響しない（2026-10-17）

セッションが生きている状態で、別のタブから `https://duet.doshisha.ac.jp/betterduet-landing` を開いた。404 が返った。その後 `fetch` でメニューのアクションを POST すると、正常な画面が返った。検証用の拡張機能のコンテンツスクリプトは、この 404 のページでも動いた。

### E-012 GET を DUET に届く前に付け替えられる（2026-10-17）

`declarativeNetRequest` のセッションルールで、`^https://duet\.doshisha\.ac\.jp/gakusei/html/` に当たる `main_frame` の GET を `/betterduet-landing?gate=1` にリダイレクトした。ホームの URL を開くと、Chrome の中で 307 として付け替えられ、DUET には GET が届かなかった（通信の記録で確認）。その後もセッションは生きていた。

### E-013 404 のページから画面を開き直せる（2026-10-17）

E-012 で付け替えられたタブで、最新の画面の `menuform` と同じ `action` と hidden 項目を持つフォームを作り、`menuform:goFb01701g` を入れて送信した。タブに「お知らせ」が正常に表示された。

### E-014 再読み込みは GET になる（2026-10-17）

E-012 のルールをオンにしたまま、POST で表示した画面を `chrome.tabs.reload` で再読み込みした。送られたのは GET で、ルールで付け替えられた。確認ダイアログは出なかった。その後、そのタブを E-013 の方法で開き直せた。

### E-015 タブの複製は GET になる（2026-10-17）

E-012 のルールをオンにしたまま、DUET のタブを `chrome.tabs.duplicate` で複製した。新しいタブから GET が送られ、ルールで付け替えられた。

### E-016 破棄されたタブに戻ると GET になる（2026-10-17）

DUET のタブを `chrome.tabs.discard` で破棄した。タブ ID が変わった（例：…111 → …124）。そのタブを読み込み直すと GET が送られ、E-012 のルールで付け替えられた。

### E-017 「戻る」を拡張機能が受け取れる（2026-10-17）

`world: "MAIN"`、`run_at: "document_start"` のスクリプトで `window.addEventListener` を差し替え、`popstate` の登録を握りつぶした。DUET の画面で `history.back()` を呼ぶと、拡張機能側の `popstate` だけが呼ばれ、DUET の警告は出なかった。ページは同じ画面のままだった。
