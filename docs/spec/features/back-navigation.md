# ブラウザの「戻る」

- 状態: Implemented
- 要件 ID の接頭辞: `BACK`
- 最終更新: 2026-10-19

## この機能が解決すること

DUET では、ブラウザの「戻る」を押すと「ブラウザの『戻る』ボタンは利用できません」という警告が出て、何も起きません。BetterDuet は、「戻る」を押したらそのタブで1つ前に見ていた画面を開き直すようにします。

DUET は自分で `pushState` をしているため、「戻る」を押してもページは移らず、`popstate` が起きるだけです（E-017）。BetterDuet は DUET より先にこの `popstate` を受け取り、DUET の警告の代わりに、前の画面を開き直します。

## 利用者から見た動き

- ホーム → 成績確認 → お知らせ と進んだタブで「戻る」を押すと成績確認が、もう一度押すとホームが表示される
- 詳細画面から「戻る」を押すと、その一覧のメニュー画面が表示される
- 「進む」は使えない

## 要件

### BACK-001 DUET の「戻る」の警告を出さない

- 状態: Implemented
- 優先度: 必須

早期フックで、DUET の `popstate` の監視が登録されないようにする（E-017）。DUET が読み込み時に行う `pushState` はそのまま残す。これにより「戻る」を押してもページは移らず、`popstate` は拡張機能だけが受け取る。

受け入れ条件:
- DUET の画面で「戻る」を押しても、「ブラウザの『戻る』ボタンは利用できません」の警告が出ない

### BACK-002 「戻る」で1つ前の画面を開き直す

- 状態: Implemented
- 優先度: 必須

`popstate` を受け取ったら、すぐに `pushState` で履歴を1つ積み直し、次の「戻る」も受け取れるようにする。そのうえで、そのタブの画面の履歴（CORE-002）から、1つ前の画面を開き直す。

- 1つ前の画面がメニュー画面なら、その画面を開く
- 1つ前の画面が詳細画面なら、その詳細画面の戻り先のメニュー画面を開く。今の画面と同じメニュー画面になる場合は、さらにその前の画面を対象にする
- 開くときは、送信係を通して、最新の画面の型のフォームに、その画面を開くアクション（ホームなら `unloadform:goHome`）を入れて送信する。開いた画面は、履歴に新しく積まず、履歴の位置を1つ戻す
- 開いた結果、タブは最新のタブになる

「戻る」で開き直す送信も、ほかの送信と同じく CORE-003 の順番に従う。

そのタブで送信を出したあと、次の画面が読み込まれるまでは「戻る」を受け流す（DUET 自身も送信中は「戻る」を受け付けない）。受け流すのは最長30秒とする。ダウンロードの送信（CORE-005）は画面が移らないため、送信係が終わったとみなすのと同じ3秒で受け流しをやめる（Q-BACK-1）。

受け入れ条件:
- ホーム → 成績確認 → お知らせ と進み、「戻る」を押すと成績確認が表示される。もう一度押すとホームが表示される
- 登録科目一覧 → 科目の詳細画面 と進み、「戻る」を押すと登録科目一覧が表示される
- ほかのタブで操作したあとの古いタブで「戻る」を押しても、どのタブもエラー画面にならない
- お知らせ → 登録科目一覧 と進んでダウンロードを押し、その5秒後に「戻る」を押すと、お知らせが表示される

### BACK-003 戻る先がないときは何もしない

- 状態: Implemented
- 優先度: 必須

そのタブの履歴に1つ前の画面がないときは、送信しない。NOTICE-BACK-1 の帯を出す。

受け入れ条件:
- SSO ポータルから開いた直後のホームで「戻る」を押すと、画面は移らず NOTICE-BACK-1 の帯が出る

### BACK-004 「戻る」のキー操作も使える

- 状態: Implemented
- 優先度: 推奨

DUET は Alt+← を無効にしている（[duet-platform.md](../duet-platform.md) の「画面側の制限」）。早期フックで、Alt+← が DUET の keydown の処理に届かないようにし、ブラウザの「戻る」として働かせる。マウスの「戻る」ボタンは DUET に止められていないため、そのまま BACK-002 になる。

Alt+→（進む）、Backspace、F5 などのほかのキーは変えない。

受け入れ条件:
- DUET の画面で Alt+← を押すと、BACK-002 と同じく1つ前の画面が表示される

## 既知の制限

ページを一度も操作していない状態（SSO ポータルから開いた直後など）でツールバーの「戻る」を押しても、何も起きない（E-031）。Chrome が、利用者の操作なしに追加された履歴を「戻る」で飛ばすためと考えられる。BACK-002 は働かないが、DUET へのリクエストもなく、セッションは壊れない。ページ内を一度操作すれば、BACK-002 のとおり動く。

ダウンロードを送ってから3秒間は、「戻る」を押しても何も起きない（BACK-002）。

## お知らせの文言

| ID | 種類 | 本文 | ボタン |
|---|---|---|---|
| NOTICE-BACK-1 | 情報 | これより前の画面はありません。 | なし |

## 今回は対象にしないこと

- **「進む」**：「戻る」で開き直した画面の先へ進む操作。必要になったら、履歴の位置を進める形で追加できる
- **詳細画面への「戻る」**：詳細画面を開き直すには、そこまでの操作を順に送り直す必要があるため、今回は戻り先のメニュー画面で代える

## 未決事項

### Q-BACK-1 ダウンロードのあと、「戻る」を受け流す時間をどうするか

早期フックは、送信を出してから30秒間、`popstate` を受け流していた（送信の途中では戻らないようにするため）。ダウンロードは画面が移らないので、ダウンロードのあと30秒間は「戻る」を押しても何も起きず、お知らせも出なかった（2026-10-19 に実機で確認。Issue #7）。

- A：今のまま。実装の変更はない。利用者は、ダウンロードの直後に「戻る」が効かない理由が分からない
- B：ダウンロードの送信では、送信係が終わったとみなす時間（CORE-005 の3秒）に合わせて受け流しを解く。早期フックがアクション名を見て、ダウンロードかどうかを判断する必要がある
- C：受け流している間に「戻る」が押されたら、お知らせを出す。新しい文言（NOTICE-BACK-2 など）を決める必要がある

答え（2026-10-19、メンテナーが「直せるなら直す」と判断）：B にした。3秒は、送信係がダウンロードを終わったとみなす時間と同じなので、受け流しをやめた時点で次の送信も順番待ちなしに送れる。C は、3秒の間に押される場面が少なく、新しい文言を増やすほどではないため見送った。BACK-002 の本文に反映した。

## 確認の記録

2026-10-17 に、Chrome 155 に `extension/` を読み込み、実際の DUET で確認しました。`node --test tests/*.test.js` もすべて通っています。

| 要件 | 確認方法 |
|---|---|
| BACK-001 | 実機：「戻る」を押しても DUET の警告が出なかった |
| BACK-002 | 実機：ツールバーの「戻る」ボタン（本物のマウス操作）と `history.back()` で、1つ前の画面が開いた。詳細画面から戻ると一覧が開いた。テスト：`tests/core.test.js` |
| BACK-003 | 実機：履歴の先頭で戻ると NOTICE-BACK-1 が出て、画面は移らなかった |
| BACK-004 | 実機：本物のキーボード入力の Alt+← で1つ前の画面が開いた（拡張機能の外から送ったキー入力では、Chrome の「戻る」は動かなかった） |

2026-10-19 に、「既知の制限」に書いた2つの挙動を実機で確かめました。ページを一度も操作していない状態での「戻る」は E-031 にあります。ダウンロードのあとの「戻る」は、登録科目一覧でダウンロードした約8秒後に本物のキー入力の Alt+← を押すと何も起きず（キーはページに届いていた）、約48秒後に押すと1つ前の画面（お知らせ）が開きました。

同じ日に Q-BACK-1 を B で直したあと、お知らせ → 登録科目一覧 と進んでダウンロードし、約6秒後に本物のキー入力の Alt+← を押すと、お知らせが開きました（BACK-002 の受け入れ条件）。テスト：`tests/early-hook.test.js`（ダウンロードは3秒、ほかの送信は30秒で受け流しをやめる。前の送信のタイマーで、あとの送信の受け流しが解けない）。
