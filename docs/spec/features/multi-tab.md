# 複数タブでの利用

- 状態: Draft
- 要件 ID の接頭辞: `TAB`
- 最終更新: 2026-10-17

## この機能が解決すること

DUET を2つ以上のタブで開いても、どのタブもログアウトされず、それぞれのタブで操作を続けられるようにします。

原因は、サーバーがセッションごとに「現在の画面」を1つしか持たず、それに合わないリクエストでセッションを破棄することにあります（[duet-platform.md](../duet-platform.md)）。BetterDuet は、サーバーの現在の画面を全タブで共有して追跡し、各タブからの送信をそれに合わせて送り直すことで、この制約を利用者から見えなくします。

## 仕組みの概要

この節は要件ではなく、要件を読むための前提です。

- 拡張機能は、DUET の画面が読み込まれるたびに、その画面のフォームの形（送信先と hidden 項目名）を記録し、全タブで共有します。これが「サーバーの現在の画面」です
- どのタブの送信も拡張機能がいったん受け取り、1つずつ順番に送ります
- 送信元のタブが最新の画面なら、そのまま送ります
- 古いタブからのメニュー操作は、フォームを最新の画面の形に書き換えて送ります
- 古いタブからの画面固有の操作は、先にサーバーをそのタブの画面まで戻し（再同期）、それから元のフォームで送ります

## 要件

以下はすべて Draft です。未決事項が決まるまで実装しません。

### TAB-001 古いタブからメニューを押しても遷移できる

- 状態: Draft
- 優先度: 必須

別のタブでサーバーの画面が進んだあとでも、古いタブのサイドメニューを押すと、エラーにならず目的の画面が開く。

受け入れ条件:
- タブ A でホームを開いたまま、タブ B で「お知らせ」を開く。その後タブ A で「よくある質問」を押すと、タブ A に「よくある質問」が表示される
- 操作のあと、タブ A とタブ B のどちらでメニューを押しても、ログアウトされない

### TAB-002 DUET の画面を新しいタブで開ける

- 状態: Draft
- 優先度: 必須

DUET のリンクを、今のタブを残したまま新しいタブで開ける。開き方は Q-TAB-1 で決める。

受け入れ条件:
- タブ A のサイドメニュー「成績」を新しいタブで開くと、タブ B に成績の画面が表示され、タブ A は元の画面のまま残る
- その後、タブ A とタブ B のどちらでメニューを押しても、ログアウトされない

### TAB-003 DUET への送信を1つずつ順番に送る

- 状態: Draft
- 優先度: 必須

複数のタブでほぼ同時に操作しても、DUET への送信が重ならない。前の送信の応答を受け取り、サーバーの現在の画面を更新してから、次の送信を始める。

受け入れ条件:
- 2つのタブでメニューを続けて素早く押しても、両方のタブが目的の画面になり、ログアウトされない

### TAB-004 古いタブの画面固有の操作を、再同期してから送る

- 状態: Draft
- 優先度: 推奨

古いタブで、その画面にしかない操作（一覧の行を押すなど）をしたとき、サーバーをそのタブの画面まで戻してから送信する。再同期の範囲は Q-TAB-2 で決める。

受け入れ条件:
- （Q-TAB-2 が決まってから書く）

### TAB-005 送り直せないときは、送らずに知らせる

- 状態: Draft
- 優先度: 必須

再同期の手順がわからない画面など、セッションを壊さずに送れることを保証できない場合は、送信を止め、そのタブで何が起きたかと次にできることを表示する。セッションを壊すおそれのあるリクエストは送らない（[product.md](../product.md) の P-1）。

受け入れ条件:

## 未決事項

### Q-TAB-1 新しいタブで開く操作をどうするか

DUET のリンクは `href="#"` なので、ブラウザ標準の中クリックや Ctrl+クリックはそのままでは効きません。

- 案 A：中クリックと Ctrl+クリックを拡張機能が受け取り、新しいタブで開く。ブラウザの普段の操作と同じで覚えることがない
- 案 B：右クリックメニューに「新しいタブで開く」を足す。`contextMenus` の権限が新たに必要になる
- 案 C：メニュー項目の横に小さなボタンを付ける。見た目が変わる

案 A と案 B は併用できます。

### Q-TAB-2 再同期をどこまで対応するか

サイドメニュー直下の画面は、メニューのアクションを1回送れば戻せます。一覧から行を選んで開く画面などは、そこまでの操作を順に送り直す必要があり、手順を記録する仕組みが要ります。

- 案 A：最初はサイドメニュー直下の画面だけ再同期する。それより深い画面の古いタブは TAB-005 で止める
- 案 B：タブごとに、その画面にたどり着くまでの送信を記録し、すべて送り直す。対応範囲は広いが、送り直しの途中で失敗したときの扱いが難しい

### Q-TAB-3 状態を変える操作を対象にするか

履修登録やアンケートの送信などを古いタブから行った場合の扱いです（[product.md](../product.md) の P-4）。

- 案 A：対象外にする。最新の画面でないタブからの送信は止め、TAB-005 の表示を出す
- 案 B：画面固有の操作と同じく再同期してから送る

### Q-TAB-4 送れなかったときに何を表示するか

TAB-005 で送信を止めたとき、利用者にどう伝えるか。表示する場所（画面上部の帯、トーストなど）と、案内する次の操作（このタブを最新にする、別のタブに移る、など）を決めます。

### Q-TAB-5 タブを再読み込みしたときの扱い

再読み込み（F5）は GET または POST の再送信になるため、セッションを破棄すると考えられます（未検証）。DUET は F5 キーを無効にしていますが、ブラウザのボタンからの再読み込みは止められません。

- 案 A：再読み込みを検知したら、そのタブで表示していた画面をメニューのアクションで開き直す
- 案 B：この機能の対象外とし、別の機能（「戻る」・ショートカットキー）の仕様で扱う
