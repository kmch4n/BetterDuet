# BetterDuet の仕様書

BetterDuet は仕様駆動開発（Spec-Driven Development）で作ります。このフォルダの文書が、拡張機能がどう動くべきかを決める唯一の正本です。コードはこの仕様に従って書き、仕様にない動作はコードの側で勝手に決めません。

初めて読む人は、この README、[product.md](product.md)、[architecture.md](architecture.md) を通読してください。[duet-platform.md](duet-platform.md) と `features/` 以下は、該当する作業をするときに引けば十分です。

## 文書の構成

| ファイル | 内容 |
|---|---|
| [product.md](product.md) | 目的、対象範囲、やらないこと、全機能に共通する原則 |
| [architecture.md](architecture.md) | 用語、拡張機能の部品、全機能に共通する要件（CORE）、お知らせ帯（NOTICE） |
| [duet-platform.md](duet-platform.md) | DUET の挙動の仕様書。確かめた事実と実験の記録を書き足していく |
| `features/*.md` | 機能ごとの要件。1機能1ファイル |

## 開発の流れ

変更は必ず仕様から始めます。

1. **仕様を書く**：`features/` に要件を追加するか、既存の要件を書き換える。状態は `Draft` にする
2. **合意する**：メンテナーが内容を確認し、`Accepted` に変える。未決事項が残っている要件は `Accepted` にしない
3. **実装する**：`Accepted` の要件だけを実装する。テスト名やコメント、Pull Request に要件 ID を書く
4. **完了を記録する**：実装と同じ変更の中で、状態を `Implemented` に変え、確認の方法（テスト名や手動確認の手順）を書く

実装の途中で仕様の穴や矛盾が見つかったら、コードで埋めずに作業を止め、仕様の「未決事項」に追記してから相談します。コードと仕様が食い違っている場合は、仕様が正しいものとして扱います。

## 要件の書き方

要件には、機能ごとの接頭辞と3桁の番号で ID を付けます（例：`TAB-001`）。一度振った ID は、要件を削除しても再利用しません。

```markdown
### TAB-001 古いタブからメニューを押しても遷移できる

- 状態: Draft
- 優先度: 必須

別のタブで画面を進めたあとに、古いタブのサイドメニューを押しても、エラーにならず目的の画面が開く。

受け入れ条件:
- タブ A でホームを開いたまま、タブ B で「お知らせ」を開く。その後タブ A で「よくある質問」を押すと、タブ A に「よくある質問」が表示される
- どちらのタブもログアウトされない

確認方法: （Implemented にするときに書く）
```

- **状態**：`Draft`（検討中）、`Accepted`（実装してよい）、`Implemented`（実装と確認が済んだ）、`Deprecated`（廃止。理由を書いて残す）
- **優先度**：`必須`（これがないと機能として成り立たない）、`推奨`（あるべきだが、後回しにできる）
- **受け入れ条件**：誰が試しても同じ判定になるよう、操作と結果で書く。「快適に」「適切に」のような判定できない言葉は使わない

## 未決事項の扱い

決まっていないことは、各ファイルの「未決事項」の節に `Q-<機能>-<番号>` の形で書き、選択肢と、それぞれを選んだ場合の影響を添えます。決まったら答えを書き込み、関係する要件に反映します。決定の理由は消さずに残します。
